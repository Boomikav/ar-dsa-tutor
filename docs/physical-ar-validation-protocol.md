# Physical Mobile AR Validation Protocol

**Project:** A Generative AI-Driven Augmented Reality Framework for Personalized Data Structures and Algorithms Learning  
**Short Name:** AR-DSA Tutor  
**Protocol Version:** 1.0.0 (Phase 11)  
**Classification:** Manual Empirical Device Protocol  

---

## 1. Protocol Purpose & Scope

This protocol establishes a standardized, reproducible procedure for validating the **AR-DSA Tutor** on physical mobile handheld hardware (e.g., Android devices running Google Play Services for AR / ARCore, and iOS devices with WebXR-compatible runtimes).

### Empirical Validation Invariant
- Software unit tests and desktop WebXR simulations verify API contracts and state machine transitions.
- **Physical AR Validation** requires testing on an actual physical mobile device equipped with camera sensors, IMU hardware, and 6DoF tracking capabilities.
- Zero simulated or pre-recorded camera video feeds are permitted.

---

## 2. Test Environment Requirements

1. **Hardware:**
   - Physical handheld smartphone or tablet.
   - Back-facing camera and motion tracking sensors (accelerometer, gyroscope).
   - Operating System: Android 11+ with ARCore installed, or iOS 16+ with compatible WebXR browser (e.g., WebXR Viewer).
2. **Network & Security:**
   - Connection via **HTTPS** with a valid SSL/TLS certificate (mandatory for WebXR device access outside localhost).
   - Direct WiFi or mobile data access to the deployed Node server (`/api/ai/*`).
3. **Physical Testing Space:**
   - A well-lit indoor environment (300–500 lux).
   - A flat, textured horizontal surface (e.g., wooden table, patterned desk, or textured floor) of at least 1.0 m × 1.0 m.
   - Avoid featureless surfaces (e.g., glossy glass, uniform white laminate).

---

## 3. Standardized Test Cases

### Test AR-01 — Capability & Secure Context Detection
* **Objective:** Verify that the browser runtime correctly detects HTTPS and genuine WebXR `immersive-ar` capability without false assumptions.
* **Procedure:**
  1. Open the deployed HTTPS URL in Google Chrome (Android) or WebXR-enabled browser.
  2. Navigate to **Profile** $\rightarrow$ **Settings** $\rightarrow$ **AR Diagnostics**.
  3. Inspect the `ARCapabilityReport` generated by `ARCapabilityDiagnostic`.
* **Verification Criteria:**
  - `secureContext` is `true`.
  - `navigatorXRAvailable` is `true`.
  - `immersiveARSupported` accurately reflects hardware support.
  - Software capability detection does **not** falsely mark `physicalARValidated` as `true`.
* **Record Format:**
  ```text
  Test ID: AR-01
  Device: [e.g., Google Pixel 7]
  OS: [e.g., Android 14]
  Browser: [e.g., Chrome 124.0]
  Result: [PASS / FAIL / PENDING]
  Observed Output: [Summary]
  Evidence File: docs/evidence/ar/AR-01-capability/[filename]
  ```

---

### Test AR-02 — Real-World Surface Hit-Testing
* **Objective:** Verify genuine real-world surface hit-testing using `XRHitTestSource` and `XRFrame.getHitTestResults()`.
* **Procedure:**
  1. From the Topic Explorer, select **Binary Search Tree** (`ds-binary-search-tree`).
  2. Tap **Launch AR Session**.
  3. Tap **Enter WebXR AR** to initiate camera passthrough.
  4. Slowly point the camera at a 45-degree angle toward the textured horizontal table surface.
  5. Move the device smoothly in a gentle circular arc over the surface.
* **Verification Criteria:**
  - Status transitions from `INITIALIZING` $\rightarrow$ `SCANNING` $\rightarrow$ `SURFACE_DETECTED` $\rightarrow$ `PLACEMENT_READY`.
  - A cyan circular reticle indicator appears projected flat on the physical surface.
  - The reticle updates position continuously as the camera moves, remaining aligned to the physical surface plane.
* **Record Format:**
  ```text
  Test ID: AR-02
  Device: [Device Name]
  Surface Type: [e.g., Textured wood grain desk]
  Detection Latency: [Measured seconds to reticle lock]
  Result: [PASS / FAIL / PENDING]
  Evidence File: docs/evidence/ar/AR-02-surface-detection/[filename]
  ```

### Test AR-03 — Surface Placement & 6DoF Spatial Tracking
* **Objective:** Anchor the 3D Binary Search Tree in world-space coordinates and confirm 6DoF tracking stability.
* **Procedure:**
  1. With the reticle indicator locked on the surface (`PLACEMENT_READY`), tap the screen.
  2. Observe the 3D BST model placement (Root node 50, children 30, 70, 20, 40).
  3. Step backward 1 meter, walk 90 degrees to the left, walk 90 degrees to the right, and tilt the device to view the tree from above.
* **Verification Criteria:**
  - Session transitions to `PLACED`, then locks into `TRACKING`.
  - The 3D BST maintains its physical coordinates on the table surface without significant drifting, jumping, or orientation flipping.
  - Reticle disappears upon placement.
* **Record Format:**
  ```text
  Test ID: AR-03
  Device: [Device Name]
  Tracking Stability: [STABLE / DRIFTING / LOST]
  Result: [PASS / FAIL / PENDING]
  Evidence File: docs/evidence/ar/AR-03-placement/[filename]
  ```

### Test AR-04 — Interactive Practice & Deterministic DSA Authority
* **Objective:** Execute an interactive BST insertion practice session in AR, verifying deterministic authority over misconceptions.
* **Procedure:**
  1. Note practice target: Target value `40`, starting at Root node `50`.
  2. In the AR Tutor HUD, make a deliberate incorrect move by tapping **Right** (claiming $40 > 50$).
  3. Observe system response.
  4. Tap **Left** (correct move: $40 < 50$), advancing pointer to node `30`.
  5. Tap **Right** (correct move: $40 > 30$), completing insertion.
* **Verification Criteria:**
  - Incorrect decision is authoritatively rejected by `BSTPracticeEngine`.
  - Node pointer remains locked at 50; tree structure is not corrupted.
  - Misconception diagnosis (`BST_WRONG_DIRECTION`) is dispatched to the multi-agent AI orchestrator.
  - AR Tutor HUD displays grounded Socratic/remedial guidance.
  - Subsequent correct decisions advance the pointer smoothly and complete the task.
* **Record Format:**
  ```text
  Test ID: AR-04
  Target Value: 40
  Misconception Diagnosed: BST_WRONG_DIRECTION
  Deterministic Authority Preserved: [YES / NO]
  Result: [PASS / FAIL / PENDING]
  Evidence File: docs/evidence/ar/AR-04-interaction/[filename]
  ```

---

### Test AR-05 — AI Failure & Offline Fallback Resilience
* **Objective:** Confirm that AR interaction remains fully functional even if the backend AI server is unreachable.
* **Procedure:**
  1. Sever backend connectivity (e.g., disable server or set invalid API route).
  2. Trigger an intentional mistake in AR.
  3. Observe system reaction.
* **Verification Criteria:**
  - The AR rendering loop and Three.js 6DoF tracking remain fluid and uninterrupted.
  - Deterministic evaluation continues locally.
  - AI Tutor cleanly displays local fallback pedagogical prompt without throwing uncaught exceptions or crashing the WebXR session.
* **Record Format:**
  ```text
  Test ID: AR-05
  Backend State: Offline / Unreachable
  AR Stability: [UNINTERRUPTED / CRASHED]
  Fallback Message Displayed: [YES / NO]
  Result: [PASS / FAIL / PENDING]
  Evidence File: docs/evidence/ar/AR-05-ai-fallback/[filename]
  ```

---

### Test AR-06 — Lifecycle Management & Resource Cleanup
* **Objective:** Verify proper disposal of WebXR sessions, hit-test sources, and Three.js GPU buffers upon exit or app pause.
* **Procedure:**
  1. While in active AR tracking, switch to another mobile app (backgrounding).
  2. Return to the browser.
  3. Tap **Exit AR** to return to the Learning Session.
* **Verification Criteria:**
  - `XRSession.end()` is invoked cleanly.
  - `XRHitTestSource.cancel()` is called.
  - WebGL context and GPU geometries are disposed without memory leaks.
  - UI returns cleanly to the 2D/3D topic view.
* **Record Format:**
  ```text
  Test ID: AR-06
  Lifecycle Event: App Backgrounding & Session Exit
  Resource Cleanup Confirmed: [YES / NO]
  Result: [PASS / FAIL / PENDING]
  Evidence File: docs/evidence/ar/AR-06-lifecycle/[filename]
  ```
